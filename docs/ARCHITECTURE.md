# 架构

```
游戏登记（games.py）：Steam App ID + 可选的 GitHub 仓库
        │
Steam / GitHub 官方 API
        │  connectors.py：分页抓取，记录请求 URL、时间、状态码
        ▼
var/raw/  原始响应（按 SHA-256 存档，只增不改）
        │  pipeline.py：字段契约校验 → 不合格记录隔离 → 去重 → 关键词归类
        ▼
var/warehouse.sqlite3  证据、版本、问题提及、跟进、AI 会话、成员
        │  analytics.py：不推荐率、30 天对比、版本前后对比、分组统计
        ▼
快照报告（JSON，存入 runs 表）
        │  api.py：FastAPI，同时托管前端构建产物
        ▼
frontend/  React 控制台 ── AI 助手 ── 本机 Codex CLI
```

## 游戏登记

- 要监控的游戏存在 `games` 表（`games.py`）：Steam App ID、名称、可选的 GitHub 仓库。添加时用 Steam 的 `appdetails` 确认条目存在且类型是游戏或 DLC，用 GitHub 接口确认仓库公开存在。
- 每次同步把当时的游戏定义写进快照配置，采集、校验（issue 和 Release 必须属于登记的仓库）和指标都只读快照里的定义。之后修改或移除游戏，不影响已有快照和离线重算。
- 没有关联仓库的游戏只抓 Steam 评论，GitHub 两个来源记为「未关联」。

## 采集与快照

- 一次同步（`sync`）生成一个快照，可以包含全部或部分游戏。原始响应先落盘，再校验、入库、计算指标；全部完成后才发布，失败的同步不会覆盖上一份结果。
- 每款游戏显示最近一次包含它的快照（`Store.latest(product)`），所以单独同步一款游戏不会让其他游戏的数据消失。
- 每个快照有一个指纹，由全部证据、版本记录、时间范围和规则版本计算得到。`replay` 用已存档的原始响应离线重新计算：规则版本没变时，指纹必须一致，否则拒绝发布；规则升级后，新快照会记录规则从哪个版本变到哪个版本。
- 字段按严格类型校验：推荐标记必须是布尔值，时间统一为 UTC，游玩时长统一为分钟，缺失值不补 0。不合格的记录进入隔离表，保留原因和原始位置。
- 同步、AI 分析和备份各自持有数据库里的任务租约（带心跳和过期回收），命令行和服务可以同时运行，不会重复执行同一类任务。

## 问题分类

`taxonomy.py` 按关键词把评论和 issue 归入六类问题，命中的词和位置会保存，用于界面高亮。GitHub issue 会先遮掉表单模板的固定内容（`###` 小标题、勾选清单、HTML 注释），否则像「(Crash) logs」这样每个 issue 都有的模板标题会被误当成玩家反馈。

## 接口与权限

- `api.py` 只监听 127.0.0.1，拒绝非本机来源的写请求，限制请求体大小。
- 本机单人模式下，所有请求都以本地管理员身份执行。团队模式（`--team`）要求每个请求携带访问令牌或企业 OIDC 令牌，并按工作区隔离跟进和 AI 会话。
- 角色：只读、分析员、复核人、管理员。确认或关闭跟进需要复核人以上；同步数据、管理成员和备份需要管理员。
- 跟进的每次变更都记录操作人、前后状态和说明。

## AI 助手

浏览器提交问题和上下文（产品、版本、问题类型或选中的反馈）→ 服务端组装事实包（当前快照的指标和原文摘录）→ 调用本机 Codex CLI → 模型可以请求有限的查询工具 → 程序核对回答 → 保存会话。

- Codex 以只读方式运行：关闭 shell、浏览器、插件和其他 MCP，使用本机已登录的账号，不复制认证文件。问题和选中的反馈会发送给 Codex 配置的模型服务。
- 查询工具有四种：按语言 / 周 / 游玩时长汇总评论、按条件取原文、查看表结构、执行只读 SQL。只读 SQL 在当前快照单独生成的 SQLite 副本上执行，禁止写入、系统表和未授权函数，限时 3 秒。每轮最多 4 次查询，最长 240 秒。
- 核对规则：回答中的每个数字必须和程序计算的值一致，引用的反馈和指标必须真实存在，否则整条回答标记为未通过。核对不保证推理正确，结论仍需人工判断。

## 备份

`backup` 生成一致性数据库副本和全部原始响应的压缩包，附带逐文件 SHA-256 清单，不包含访问令牌。`restore-drill` 把备份恢复到新目录，校验文件、数据库完整性和最新快照指纹，不影响正在使用的数据。
