# 指标口径

所有指标由 `src/quality/analytics.py` 统一计算，界面、导出和 AI 助手使用同一份结果。时间一律按 UTC 计算，界面显示为本地时间。

## 不推荐率

不推荐评论数 ÷ 评论总数。来自玩家在 Steam 写评论时选择的「推荐 / 不推荐」（`voted_up`）。

- 分母包含所有语言和短评论；问题分类、语言识别等其他环节不会改变这个分母。
- 它反映写评论的玩家的推荐意愿：不是全部玩家的满意度，也不是对评论文字的情绪判断。
- 单期比例的 95% 区间用 Wilson 方法，样本里没有差评时上限也不为 0。

## 最近 30 天的变化

比较最近 30 天与之前 30 天的不推荐率，两段时间各需至少 50 条评论，且评论采集完整。

| 判断 | 条件 |
|---|---|
| 明显变差 / 明显好转 | 两期差值的 95% 区间（Newcombe 方法）不包含 0 |
| 需要排查 | 差值至少 +5 个百分点且区间下限大于 0；参与语言调整的评论占两期各 80% 以上；按语言构成调整后、按 7 天为块重新抽样后，区间下限仍大于 0 |
| 可能变差 | 差值区间大于 0，但没有通过上一行的稳健性检查 |
| 无明显变化 | 区间包含 0 |
| 样本不足 / 数据不完整 | 不满足样本量或采集完整性条件，只显示数值，不做判断 |

- **按语言调整**：只取两期都至少有 10 条评论的语言，用两期合并的评论数作为权重，计算加权后的差值和 2,000 次重抽样区间。它排除的是「评论者语言构成变了」这一种解释，不能排除其他因素。
- **按周重抽样**：按天汇总后以 7 天为块循环重抽样 2,000 次，检查结论是否依赖少数几天。
- 随机种子固定为 20261013，结果可复现。

## 版本前后对比

以 GitHub Release 的发布时间为界，比较发布前 14 天和发布后 14 天的不推荐率。

- 两段各需至少 30 条评论，且时间段完整落在采集范围内，才给出「明显变差 / 明显好转 / 无明显变化」；否则标为「数据不完整」或「样本不足」，仍然显示已有的数值。
- 前后 14 天内还有其他版本时会列出，此时变化不能单独归因到某一个版本。
- 同一款游戏的多个版本一起计算 p 值时，用 Benjamini–Hochberg 方法校正（AI 助手可见），不挑选显著的版本单独报告。
- GitHub 发布时间不等于玩家在 Steam 上收到更新的时间。没有对照组，版本前后的变化是观察结果，不是版本造成的效果。

## 问题类型

按关键词把评论和 issue 归入六类：崩溃与稳定性、性能与卡顿、联机与连接、操作与界面、成长与引导、平衡与机制。

- 评论支持英文、中文（简繁）和俄文；其他语言的评论不参与归类，但仍计入不推荐率。
- GitHub issue 先遮掉表单模板的固定内容（`###` 小标题、勾选清单、HTML 注释）再匹配。
- 一条反馈可以同时属于多类。「近 30 天」「之前 30 天」只统计 Steam 评论，和「最近 30 天的变化」使用同一时间段。
- 关键词归类没有经过人工抽检验收，是帮助快速定位原文的线索，不是缺陷确认。

## 游玩时长分组

按写评论时的累计游玩时长分为 2 小时以内、2–20 小时、20 小时以上；平台没有返回时长的单独归为「时长未知」。分组描述的是不同评论者的差异，不是留存或付费分层。

## 数据边界

- 写评论的玩家是主动发声的一部分人，统计区间只反映抽样误差，不能消除这种偏差。
- GitHub issue 主要来自开发者和核心玩家，与 Steam 评论是不同人群，两者的数量不合并计算。
- 没有安装、付费、留存数据，系统不计算流失率、收入或 LTV；AI 助手被要求在这类问题上说明数据不支持。
